# Apple HIG 设计框架

> Apple 设计 = **克制** + **一致** + **人性化**

## 框架概览

本框架基于 Apple Human Interface Guidelines（HIG）官方文档和 WWDC 公开演讲内容，为 macOS 和 iOS 双平台提供可执行的设计决策支持。不是模仿 Apple 的「感觉」，而是提取其背后的系统化方法。

**适用场景**：
- iOS/macOS原生 App 设计
- Cross-platform 项目需要符合 Apple 设计规范
- Design review 时的客观检查清单
- 向利益相关者解释设计决策

**核心假设**：Apple 设计师不做无意义的创新。遇到设计问题前，先看能否用现有模式解决。

---

## 核心心智模型 (4 个)

每个模型都通过三重验证：**跨域复现**（在不同页面/功能中出现）+ **生成力**（能推断新问题的方案）+ **排他性**（不是通用 UX 原则）。

### 模型 1：层次即功能

> **视觉层级反映功能优先级，而不是独立的美学选择。**

| 维度 | 内容 |
|------|------|
| **来源证据** | macOS HIG「Typography」章节、「Visual Hierarchy」原则；WWDC2023 "Organize your interface" |
| **应用场景** | 画原型时先标记 3 个最重要的元素，确保它们的字号/对比度/间距最突出 |
| **失效条件** | Landing Page / 营销页可能需要打破常规吸引注意 |
| **反例** | 所有按钮同样大小，用户找不到主要操作 |

**实践检查表**：
- [ ] 页面标题是否明显大于正文？
- [ ] 主要操作的颜色/位置是否最醒目？
- [ ] 次要信息是否通过灰色/缩小/折叠降低视觉权重？

---

### 模型 2：一致性带来清晰

> **遵循平台惯例比「独特设计」更能降低学习成本。**

| 维度 | 内容 |
|------|------|
| **来源证据** | 所有 native apps 统一导航模式（Tab Bar / Sidebar）；HIG 组件库的强制性说明 |
| **应用场景** | 优先使用 Tab Bar / Navigation Bar / Settings List 等标准组件，而非自定义 UI |
| **失效条件** | 品牌差异化强的营销活动页、游戏类应用 |
| **反例** | 左滑删除变成点击图标，用户找不到手势区域 |

**实践检查表**：
- [ ] 导航模式是否符合平台惯例（iOS→底部 Tab，macOS→顶部/Sidebar）？
- [ ] 按钮样式是否与系统组件一致（SF Symbols / System Color）？
- [ ] 交互动效是否遵循 platform standard（如返回手势）？

---

### 模型 3：尊重用户时间

> **减少每一步操作都是对用户时间的投资。**

| 维度 | 内容 |
|------|------|
| **来源证据** | Apple Design Awards 获奖案例普遍步骤更少；haptics 减少认知负荷的研究 |
| **应用场景** | 每增加一步操作前问「这真的必要吗？」；表单验证从实时改为失焦验证 |
| **失效条件** | 需要教育用户的创新功能可以接受短期复杂度（但需提供引导） |
| **反例** | 简单设置需要 5 级菜单才能找到 |

**实践检查表**：
- [ ] 能否从 3 步减到 2 步？
- [ ] 加载>3 秒是否显示了进度反馈？
- [ ] 错误提示是否给了明确的解决路径？

---

### 模型 4：平台为伙伴

> **调用系统 API 比重复造轮子更稳健。**

| 维度 | 内容 |
|------|------|
| **来源证据** | SwiftUI 声明式语法的设计理念；System Color 自动适配深色模式 |
| **应用场景** | 优先使用 `UIColor.systemBlue` 而非自定义蓝色；用 native picker 而非自定义日期选择器 |
| **失效条件** | 跨平台项目需平衡各平台差异 |
| **反例** | 自定义的「夜间模式」切换导致颜色不一致 |

**实践检查表**：
- [ ] 是否用了 System Color 而非固定色值？
- [ ] 是否调用了 Dynamic Type 支持？
- [ ] 是否需要自定义组件？能否用现有的替代？

## 决策启发式库（16 条，按维度组织）

### 🎨 配色建议

| # | 场景 | 建议 | 原因 | 案例 |
|---|------|------|------|------|
| 1 | 不确定用什么颜色 | 用 System Color | 自动适配深色/浅色模式 | Settings, Notes 所有原生 App |
| 2 | 强调状态（未读/激活） | 饱和度变化而非色相切换 | 保持视觉连贯性 | Mail 的未读邮件高亮 |
| 3 | 数据可视化 | 语义色（绿好/红差）而非彩虹配色 | 利用认知惯性降低理解成本 | Numbers 红绿区分涨跌 |
| 4 | Primary Button / CTA | System Blue 或黑色 | 符合用户心智模型（蓝色=可点击） | 所有原生 App 的确认按钮 |
| 5 | 错误提示 | 红色 + 图标 + 说明文字 | 多重编码提升识别率（颜色≠唯一信号） | Safari 网络错误处理 |
| 6 | Disabled 状态 | 透明度降至 30-40% | 不突兀但仍可辨识 | Switch Control 的关闭状态 |

### 🖱️ 交互建议

| # | 场景 | 建议 | 原因 | 案例 |
|---|------|------|------|------|
| 7 | 删除操作 | Swipe → Delete（iOS）/ Confirm Dialog（macOS） | 触屏防误触 vs 鼠标精准 | Mail、Messages App |
| 8 | 表单输入验证 | 失焦时验证（非实时） | 平衡体验与性能，避免频繁 API 调用 | iCloud Keychain 密码框 |
| 9 | 加载时间预估 > 3 秒 | 显示进度反馈（进度条/百分比） | 防止用户焦虑和意外关闭 | Photo Library 导入大文件夹 |
| 10 | 危险操作 | 提供「撤销」选项 | 降低试错成本，培养安全感 | iMessage 撤回功能、Safari 关闭多个标签 |
| 11 | 主要操作区域 | iOS 底部右侧拇指热区 | Fitts' Law 优化 | Instagram bottom Tab、微信消息按钮 |
| 12 | 长列表滚动 | Section Header 分组 | 降低认知负荷，辅助导航定位 | Contacts App |

### 📐 布局建议

| # | 场景 | 建议 | 原因 | 案例 |
|---|------|------|------|------|
| 13 | 首屏信息密度 | ≤3 个重点 | Hick's Law：选择数越多决策越慢 | Settings 首页卡片、Apple TV 推荐位 |
| 14 | 长列表导航 | Section Header + Sticky Header | 辅助快速定位，保持上下文 | Notes App 搜索历史记录 |
| 15 | 响应式设计基础单位 | 8pt Grid System | 像素级对齐，缩放比例协调 | 所有 native App 的 padding/margin |
| 16 | Touch Target 尺寸 | ≥44x44pt | WCAG AA 最低要求，覆盖成年人大拇指 | Apple Music 播放控制按钮 |
| 17 | 安全区域适配 | Safe Area Layout Guide | 避开刘海/Home Indicator 等系统遮挡 | iPhone X 之后的所有 App |

### 💡 创新评估框架

当用户提出「想要酷炫效果」时使用此框架判断可行性。

| # | 场景 | 评估标准 | 决策 | 备注 |
|---|------|---------|------|------|
| 18 | AI 功能集成 | 能否显著缩短用户操作步骤？ | ✅ 采纳 | 如 Siri 快捷指令、照片智能分类 |

## 平台对比表

同一需求在 macOS 和 iOS 上的不同解决方案。

| 场景 | macOS 方案 | iOS 方案 | 原因 |
|------|-----------|----------|------|
| **删除确认** | Confirm Dialog（二次确认弹窗） | Swipe → Delete（滑动删除） | 鼠标精准 vs 触屏防误触 |
| **多窗口管理** | Split View / Mission Control | Tabs / Nested Navigation | 桌面大屏空间丰富 vs 移动单手操作 |
| **导航模式** | Sidebar（左侧边栏） | Bottom Tab Bar | 空间充足 vs 拇指热区优化 |
| **搜索入口** | ⌘K 快捷键 / Spotlight | Search Bar（顶部固定） | 键盘高效 vs 触屏便捷 |
| **上下文菜单** | 右键菜单（长按模拟） | 长按 / 3D Touch | 鼠标右键物理按键支持 |
| **模态弹窗** | Center Modal / Sheet | Full Screen Sheet | 桌面双屏友好 vs 移动端专注当前任务 |

## Agentic Protocol（回答工作流）

### Step 1: 问题分类

收到设计问题后，先判断类型：

| 类型 | 特征 | 行动 |
|------|------|------|
| **基础功能** | 登录/注册、设置页、列表页、详情页 | 直接用 HIG 标准组件，不创新 |
| **复杂交互** | 多步骤流程、数据可视化、图表 | 参考 Apple Design Awards 获奖案例 |
| **创新需求** | 「想要酷炫效果」「差异化设计」 | 先用 4 个心智模型检查必要性 |

---

### Step 2: HIG 合规性审查

对照以下检查清单逐项核对：

- [ ] **Contrast Ratio ≥4.5:1**（WCAG AA 标准）
- [ ] **Touch Target ≥44x44pt**（iOS）/ ≥10mm（macOS）
- [ ] **Keyboard Shortcuts 覆盖常见操作**（macOS 必填）
- [ ] **Dynamic Type 支持完整**（字体缩放测试）
- [ ] **Safe Area 适配正确**（刘海/灵动岛区域）
- [ ] **Dark Mode 兼容**（System Color 使用）

---

### Step 3: 输出设计建议

基于检查结果，按优先级给出具体建议：

1. **P0 必须修复**：违反 HIG 强制性条款（如 Accessibility 问题）
2. **P1 强烈建议**：严重影响用户体验（如布局混乱）
3. **P2 可选优化**：锦上添花（如动效微调）
